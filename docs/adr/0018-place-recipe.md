# ADR-0018: 장소별 2.5D 방은 한 번 생성한 레시피로 어디서나 똑같이 그린다 (제안)

*   날짜: 2026-09-10
*   상태: 제안됨 — 토의 전. 기본 방 9종(ADR-0015 개정 3)이 끝난 뒤 다음 단계로 논의한다. 확정된 결정이 아니다.

## 배경

방(ADR-0015)은 장면 종류(카페·집·식당·공원…)마다 손으로 그린 기본 방 하나다. 헬스장이나 동네 식당은 이걸로 충분하지만,
파리에 가서 에펠탑을 가거나 시흥 갯골생태공원에 가면 "공원" 기본 방이 떠서 어디를 갔는지 화면에서 알 수 없다. 여행지는
웹에서 찾아 도시 팩으로 들어오므로(ADR-0009) 장소를 미리 다 그려 둘 수는 없다. 오너의 요구(2026-09-10):

*   그때 생성하되 **재현 가능**해야 한다 — 다른 사람이 같은 곳에 가도 같은 방이 나온다.
*   **실제 랜드마크·특징**을 반영한다.
*   일반 장소(헬스장 등)는 우리가 만든 **기본 방**을 그대로 쓴다.

## 제안

**"생성"과 "재현"을 분리한다. 생성은 백엔드가 장소당 한 번 하고, 결과는 작은 레시피(JSON)로 남기며, 그리기는 레시피와 장소 id
시드로 항상 같은 순수 함수가 한다.**

### 세 층

1.  **기본 방 (손으로).** 장면 종류 10개(카페·집·식당·도서관·헬스장·쇼핑몰·박물관·공원·강변·해변)마다 하나. 레시피가 없는
    장소의 폴백이자, 레시피 조립의 템플릿이다. — ADR-0015 개정 3에서 만든다.
2.  **장소 레시피 (백엔드가 한 번 생성).** 도시 팩을 만들 때(`POST /api/trip/plan`) 장소마다 하나 더 뽑는다. 대략:
    ```json
    {
      "base": "park",                       // 템플릿 장면 종류 (실내/야외/물가는 여기서 결정)
      "hero": { "family": "tower", "tiers": 3, "color": "wood", "accent": "coral", "label": "관찰 전망대" },
      "props": ["reed", "salt-shed", "boardwalk", "mudflat-pool"],
      "ground": "mudflat", "palette": { "ground": "sun-2", "far": "mint-2" },
      "evidence": [0, 2]                    // 근거 스니펫 번호 (ADR-0009와 같은 규칙)
    }
    ```
    근거 번호가 범위 밖이거나 스키마를 벗어나면 버리고 기본 방으로 간다. 레시피는 팩과 함께 백엔드 캐시(`.cache/trip/`)와
    브라우저(`theworld.places.v1`)에 저장된다.
3.  **조립 (프론트, 순수 함수).** `recipe + rng(placeId)` → `RoomSpec`. 템플릿의 벽/지평선과 자리 골격 위에 랜드마크를 놓고,
    소품을 시드로 배치한다. 로그 줄 큐는 템플릿 장면 종류의 표를 그대로 쓴다.

### 랜드마크 그림 — 매개변수 도형 가족

레시피가 "에펠탑"이라 적어도 그림이 없으면 소용없다. 선택지와 판단:

| 방법 | 장점 | 단점 |
|---|---|---|
| 손으로 그린 카탈로그 | 확실, 스타일 일치 | 유명 장소 몇십 개가 한계. 갯골생태공원은 못 덮는다 |
| **매개변수 도형 가족** (추천) | 스타일 유지, 검증은 스키마 하나, 어떤 장소든 "알아볼 만큼" | 실물과 똑같지는 않다 |
| 모델이 SVG 직접 생성 | 무엇이든 그림 | 스타일이 매번 다르고 검증기가 필요. 재현은 캐시에만 의존 |
| 이미지 생성 → 3D화 (3d 브랜치 TripoSR) | 가장 생생 | 서버에서 한 번 만들어 캐시해야 재현. 팔레트 맞추기 어려움 |

추천: 탑·다리·문·돔·전망대·보드워크·갈대밭·분수·동상·등대 같은 **가족 20개쯤**을 그리고, 높이·층수·색·기울기를 레시피가 정한다.
에펠탑은 `tower(격자, 3단, 갈색)`, 갯골의 관찰탑은 `tower(나무, 나선, 붉은색)`, 갯골의 소금창고는 `shed(검은 지붕)`. 모델은 근거
스니펫을 보고 **어느 가족, 어떤 매개변수**만 고르고 그리기는 우리 코드가 한다. 정말 유명한 곳 10~20개만 손 카탈로그로 덮는다.

### 재현성

*   그리기는 난수를 `rng(placeId)`로만 쓴다. 같은 레시피면 누가 열어도 같은 방.
*   같은 백엔드를 쓰면 같은 팩(캐시)을 받는다. 다만 지금 팩은 서버 캐시와 브라우저에만 있으므로, "모두 같은 방"을 보장하려면
    **팩을 서버 문서로 공유**하는 결정이 하나 더 필요하다 (CONTRACT `places` 문서의 범위 — 토의 항목).

## 예시

*   **시흥 갯골생태공원**: 스니펫에 "갯벌, 갈대, 소금창고, 흔들 전망대, 나무 데크". 레시피 = base 야외·물가, hero 나무 전망탑(나선, 붉은색,
    3단), props 갈대밭·소금창고·데크길·갯벌 웅덩이, 팔레트 갈대색·갯벌 회갈색. 벤치 자리는 데크 끝, 산책 목적지는 전망탑과 소금창고.
*   **파리 에펠탑**: base 공원(잔디 광장), hero 격자 탑 3단 갈색, props 가로등·회전목마·잔디. 산책 목적지는 탑 아래와 매점.
*   **홍대 헬스장**: 레시피 없음 → 기본 헬스장 방.

## 토의할 것

1.  팩(레시피 포함)을 서버 문서로 공유할지 — 재현성의 범위.
2.  도형 가족 목록과 첫 손 카탈로그 10~20곳.
3.  레시피 추출을 팩 파이프라인의 모델 호출에 얹을지(한 번에), 별도 호출로 둘지(장소 수만큼).
4.  카메라·만화 컷은 정면 무대를 쓰기로 한 결정(ADR-0015)을 유지할지.

## 순서 (제안)

1.  기본 방 10종 — ADR-0015 개정 3 (진행 중).
2.  레시피 스키마와 조립기. 처음엔 백엔드 없이 손으로 쓴 레시피 두어 개(갯골·에펠탑)로 검증한다.
3.  도형 가족 카탈로그와 백엔드 추출 단계.
4.  팩 공유 결정.

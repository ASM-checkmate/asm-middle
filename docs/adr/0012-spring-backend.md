# ADR-0012: 서버는 Spring으로 — 저장본을 맡기고, 진짜 사람을 들이되, 시뮬레이션은 프런트에 둔다

*   날짜: 2026-09-08
*   상태: 채택됨

## 배경

*(2026-09-08 저녁 추가) 호준의 Node 백엔드에 그 사이 붙은 하루 계획(ADR-0010)·말로 하는 통화의 턴과 예열(ADR-0011)도 같은
원칙으로 옮겼다 — `llm/Plan*`·`llm/Call*`·`WarmController`. Ollama 호출은 이제 **항상 스트리밍**으로 받아 모으고(`OllamaClient.Cancel`),
`ModelLane`이 하루 계획·여행지처럼 낮은 우선순위 생성을 모아 두었다가 통화 턴이 오면 끊는다(503 `yielded to call`).
음성 서비스 `voice/`(파이썬)는 백엔드 밖에 그대로 둔다.*

ADR-0006으로 생긴 `backend/`는 Ollama 앞의 관문 하나였다 — 답장·그림 읽기·여행지 찾기의 **말과 데이터**만 지어
주고, 세계 상태(`theworld.world.v5`)·메모리·앨범·장소 팩은 전부 브라우저 localStorage에 있었다. 기기를 바꾸면
다른 세계고, 브라우저 데이터를 지우면 하루가 사라진다. FRIENDS_SPEC §4는 "서버가 붙으면 NPC 풀 자리에 실제
사용자 에이전트의 확정 일정이 들어온다"고 미뤄 두었지만, 그 서버가 없었다. 의존성 0의 Node 관문은 그 자리를
맡기엔 DB도, 인증도, 스키마 관리도 없다.

한편 프런트의 규칙 엔진은 "새로고침해도 같은 하루"를 시드로 지키고 있고(ADR-0001·0008), 그 결정성은 서버가
판단을 가져가는 순간 깨진다. 필요한 것은 판단이 아니라 **저장·동기화·다른 사람의 일정**이다.

## 결정

**Java 21 + Spring Boot 3.5의 서버 `backend/`가 (1) 문서 단위 저장·동기화, (2) 진짜 사람 에이전트의 프로필·발행
일정·겹침 조회·친구 관계, (3) LLM 어댑터를 맡는다. 굴림·판정·만화·하루 짜기는 그대로 프런트다.**

1.  **스택은 Java 21 LTS + Spring Boot 3.5.16, Gradle(Kotlin DSL).** Spring MVC(서블릿) 위에 **가상 스레드**
    (`spring.threads.virtual.enabled`), Spring Data JPA + Flyway, H2 파일(dev, PostgreSQL 모드) / PostgreSQL(prod),
    아웃바운드는 `RestClient`, Jackson, Bean Validation. Spring Boot **4.x는 고르지 않는다** — 스타터 모듈 재편과
    Jackson 3 전환 직후라 예제·라이브러리·답변이 아직 3.x 기준이고, 3.5는 최신이면서 개발자가 가장 많이 쓰는
    안정선이다. 21은 가상 스레드가 정식이 된 LTS다.
2.  **인증은 토큰 없는 고정 아이디 로그인, 비밀번호 없음** (2026-09-08 오후 개정 — 처음엔 기기 기반 익명 계정과
    Bearer 토큰이었다). 서버가 시드로 가진 아이디 다섯(`yoongwan`·`hojun`·`guest1`·`guest2`·`guest3`, 모양
    `^[a-z][a-z0-9_]{1,23}$`, `V2__seed_users.sql`) 중 하나를 고르면 끝이다. `GET /api/users`로 고르고
    `POST /api/auth/login`으로 확인한 뒤 모든 `/api/**`에 `X-User-Id: <id>`를 붙인다. 없거나 모르는 아이디면 401이고,
    프런트는 그때 저장된 사용자를 버리고 로그인 화면으로 돌아간다(서버가 죽은 것과 구분). 아이디 하나 = 에이전트 하나 =
    서버 문서 한 벌 — 같은 기기에서 다른 아이디로 들어가면 로컬 저장본을 비우고 그 아이디의 문서를 받는다.
3.  **동기화는 문서 단위, 서버는 내용을 모른다.** localStorage 저장본 4개(`world`·`memory`·`book`·`places`)를
    불투명 JSON 문서로 `PUT /api/me/docs/{name}`에 올린다 — `baseVersion`이 서버 버전과 같을 때만 갱신, 아니면
    **409에 서버본을 동봉**해 클라이언트가 정한다. 프런트 정책: 서버 `clientTs`가 내 마지막 로컬 저장보다 나중이면
    서버본을 쓰고 새로 뜬다, 아니면 `force: true`로 덮어쓴다. 앱은 뜨기 전에 3초 안에 서버가 더 새것인 문서를
    places → memory → world → book 순서로 받고(`bootstrapSync`) 그 뒤에 스토어를 만든다 — 마이그레이션·검증·catch-up은
    여전히 스토어 부팅 코드다. 저장 뒤 800 ms 디바운스로 올리고, 실패는 지수 백오프(2s→…≤60s), `pagehide`엔 keepalive.
4.  **시뮬레이션은 프런트에 남긴다** (ADR-0006 결정 5 유지). 서버는 굴림도 판정도 만화도 하지 않는다. dev 시계
    (`?dev=1`)의 scale이 1이 아니거나 서버 world의 anchor가 이 기기의 지금보다 미래면 `world`/`book`은 주고받지
    않는다 — 다른 기기가 앞당겨 산 세계를 살리면 today가 어긋난다.
5.  **진짜 사람 에이전트는 NPC 앞자리에 들어오고, 마주침은 캐시로 결정된다.** 내 확정 일정(`[anchor, now+36h]`
    창)을 `PUT /api/me/schedule`로 **창째 교체**하고, 내 활동 슬롯마다 `POST /api/agents/at`로 "그때 거기 누가 있나"를
    묻는다(같은 장소·겹침 ≥ 30분·프로필 있는 사용자·`agent.id` 오름차순·슬롯당 8명). 답은 `world.remote` 캐시에
    **활동 key마다 한 번만** 채우고, 이미 도착한 활동은 다시 묻지 않는다 — 응답이 늦게 와서 진행 중인 활동의
    실루엣이 바뀌면 안 된다. 굴림 시드는 remote 상대면 `${dayKey}:${placeId}:${[내 id, 상대 id].sort()}`라 두 기기가
    같은 결과를 보고, NPC는 기존 시드 그대로라 옛 결과가 보존된다. 말을 튼 상대는 `POST /api/friends`(대칭·멱등)로
    적고, 친구의 오늘~내일(`GET /api/friends/{id}/day`)이 동행 카드와 '지금'에 들어간다. 오프라인이면 캐시가 비고
    NPC 풀 그대로다.
6.  **LLM은 인터페이스 뒤로 옮기고 검사하지 않는다.** `backend/src/{reply,sketch,trip,search,geocode}.ts`의
    프롬프트·파서·스키마·검증 문자열을 글자 단위로 이식하고, 단위 테스트는 그 순수 로직만 본다(Node의
    `scripts/*.test.mjs` 항목 이관). 모델 호출은 "된다 치고" 넘어간다. 경로·JSON·상태 코드(400/422/502/503)는
    `docs/CONTRACT.md` 그대로라 프런트의 세 fetch가 공통 관문(`api()`)을 쓰도록만 바뀐다.
7.  **여행 파이프라인의 결함 4개를 이식하며 고친다.** (1) 조립에서 city/country 지오코딩 후보 중 도심 80 km 안인
    첫 것을 쓴다(전에는 city 결과를 무조건); (2) 스니펫 예산 22,000자를 검색어별 라운드로빈으로 채운다(한 검색이
    예산을 다 먹지 않게); (3) 프롬프트가 **실제로 들어간 번호 집합**을 돌려주고 파서는 그 집합으로 `src`를 검증한다;
    (4) 요청 전체 데드라인 100초 — 지오코딩은 데드라인까지만, 남은 장소는 근사값/버림, country 재조회는 city가
    비었을 때만. 캐시는 파일 대신 `trip_pack`/`trip_search` 테이블(모든 사용자 공유).

## 근거

*   **왜 Spring인가.** 스키마 마이그레이션(Flyway)·JPA·검증·액추에이터가 한 묶음이고, 가상 스레드로 25~100초씩
    막히는 LLM·지오코딩 호출을 스레드 걱정 없이 블로킹 코드로 쓸 수 있다. Node 관문은 의존성 0이 미덕이었지만
    DB와 인증이 붙는 순간 그 미덕이 사라진다. Java 21 + Boot 3.5는 2026년 시점에 가장 많은 사람이 같은 코드를
    쓰고 있는 조합이라 문제를 검색하면 답이 있다.
*   **왜 3.5이고 4.x가 아닌가.** 4.0은 스타터를 세분화하고 Jackson 3로 넘어가며 많은 것이 이름을 바꿨다. 새
    프로젝트라 이식 부담은 없지만, 그 변화 직후의 생태계(라이브러리·예제·답변)는 아직 3.x 기준이라 막힐 때
    비용이 크다. 3.5는 LTS 성격의 안정선이고, 4.x로 올리는 일은 나중에 스타터 이름과 Jackson 임포트를 바꾸는
    기계적 작업이다.
*   **왜 토큰 없는 고정 아이디인가.** "심심해서 켜는 앱"에 가입·비밀번호는 문턱이고, 쓰는 사람은 오너와 친구
    몇뿐이다. 처음 고른 기기 익명 계정(`deviceId` → 토큰)은 온보딩이 0초지만 **기기를 바꾸면 다른 세계**였고, 서버의
    존재 이유가 "기기를 바꿔도 같은 하루"인데 그 길이 없었다. 아이디를 고르기만 하면 어느 기기에서든 같은 문서를 받고,
    토큰·해시·재발급 코드가 통째로 사라진다. 대신 인증이 없다 — 아래 트레이드오프.
*   **왜 문서 단위이고 409인가.** 서버가 world의 모양을 알면 프런트 마이그레이션(v5)마다 서버도 바뀌어야 한다.
    불투명 문서면 서버는 버전 하나만 알고, "새로고침해도 같은 하루"의 모든 규칙은 한 곳(프런트)에 남는다.
    충돌은 드물다(한 사람이 한 기기에서 산다) — 그래서 병합 대신 **서버본을 돌려주고 클라이언트가 정하는** 가장
    단순한 정책을 택했고, 채택할 때 새로 뜨는 것은 스토어를 다시 만드는 가장 안전한 길이다.
*   **왜 시뮬레이션을 옮기지 않는가.** 결정성과 검사 가능성. 서버가 판단하면 오프라인이 곧 "세계가 멈춤"이고,
    지금의 12종 헤드리스 검사(`scripts/sim-*.test.mjs`)는 전부 서버 스텁이 된다. 서버가 없어도 앱이 그대로 도는
    것이 ADR-0006 결정 4의 약속이다.
*   **왜 마주침을 캐시로 굳히는가.** 서버 응답은 늦게 올 수 있고 다른 사람의 일정은 바뀐다. 활동 key마다 한 번만
    묻고 도착 뒤엔 다시 묻지 않으면, 한 번 본 실루엣은 그대로고 두 기기(나와 상대)가 같은 시드로 같은 굴림을
    본다. "겹침 30분"과 "id 오름차순"은 서버가 정하되 프런트가 한 번 더 정렬해 결정성을 프런트 쪽에서 보장한다.
*   **왜 LLM을 검사하지 않는가.** 오너 지시. 모델은 비결정적이고 느리며, 검사할 것은 프롬프트가 같은 글자인지와
    파서가 같은 결과를 내는지다 — 그것은 순수 함수라 Ollama 없이 검사한다(ADR-0009와 같은 패턴).
*   **왜 여행 결함을 이식하며 고치는가.** 글자 단위 이식이 원칙이지만, (1)~(4)는 실제 요청에서 드러난 결함이다 —
    country 후보가 더 정확한데 city를 쓰거나, 한 검색이 예산을 독식하거나, 번호가 잘렸는데 검증은 전체 범위로
    하거나, 지오코딩이 데드라인 없이 늘어지는 것. 고친 것마다 회귀 테스트를 둔다.
*   **버린 선택지 — Node 백엔드에 DB를 붙이기.** 의존성 0을 버리는 순간 Node의 이점이 없고, ORM·마이그레이션·검증을
    하나씩 골라 붙여야 한다. **버린 선택지 — 서버가 하루를 짠다.** 위 "왜 시뮬레이션을 옮기지 않는가".
    **버린 선택지 — 실시간(WebSocket) 마주침.** 마주침은 활동 시작 전에 한 번 정해지면 되고, 폴링(5분·recompute 뒤)으로
    충분하다.

## 영향

*   `backend/` 신설(`world.theworld.server` — `common`·`auth`·`sync`·`social`·`llm`·`trip`), `V1__init.sql`, `application.yml`
    (`theworld.*`, 환경변수 덮어쓰기), 테스트 155개(`./gradlew test`, H2 인메모리). 옛 Node 백엔드는 이식이 끝나 삭제했고(커밋 0298e8d까지가
    원본), Spring 프로젝트가 그 자리 `backend/`를 이어받았다.
*   프런트: `src/sim/api.ts`(관문·토큰), `sync.ts`(부트스트랩·푸시·발행·조회), `remote.ts`(검증·캐시 병합·발행 모양·시드),
    `agents.ts`·`timeline.ts`·`store.ts`·`places.ts` 수정, `World.remote` 캐시(v5 유지, optional), `main.tsx`가
    `bootstrapSync()` 뒤에 앱을 동적 import — 저장된 사용자가 없고 서버가 살아 있으면 그 전에 로그인 화면(`LoginScreen`).
    새 localStorage 키 `theworld.user.v1`(`{ userId, name }`)·`theworld.sync.v1`.
    `vite.config.ts`의 `BACKEND_URL` 기본 `http://localhost:8080`. 새 검사 `scripts/sim-sync.test.mjs`·`sim-remote.test.mjs`.
*   화면: DevPanel `api` 줄(backend 상태·userId·문서 버전·마지막 push·건너뛴 이유·remote 수), TopChrome은 서버가
    없을 때만 회색 점 "혼자 생각 중", FriendsOverlay의 remote 친구 '지금'.
*   `docs/CONTRACT.md`에 §2.1~2.3(인증·문서·에이전트/친구), `.claude/launch.json`에 `theworld-backend`, `backend/README.md`.
*   감수하는 트레이드오프·알려진 한계
    *   **`book` 문서가 비대하다.** 앨범이 사진 dataURL을 품어 4 MB 상한에 가장 먼저 닿고, `pagehide`의 keepalive
        flush는 브라우저 64 KB 제한 때문에 큰 문서를 못 보낸다(다음 저장·재시도가 대신한다). 사진을 별도 저장소로
        빼는 일은 다음 결정이다.
    *   **`world.journeys`가 정리되지 않는다.** 이동 기록이 anchor에 접히지 않아 문서가 자란다.
    *   **Nominatim이 전역 직렬화된다.** 서버 하나의 단일 락(1.1초 간격)이라 여러 사용자의 여행 요청이 줄을 서고,
        16곳이면 한 요청에 약 18초다. 사용자가 늘면 지오코딩 캐시나 유료 지오코더가 필요하다.
    *   **LLM 취소는 반쪽일 수 있다.** 같은 (user, batch)의 새 호출이 오면 이전 Future를 `cancel(true)`해 서버 스레드와
        Ollama로 가는 HTTP 연결을 끊는다. Ollama가 연결이 끊긴 뒤 생성을 멈추는지는 확인하지 않았다 — 멈추지 않으면
        서버 스레드만 풀릴 뿐 GPU 시간은 쓴다.
    *   **다기기 충돌은 새로 뜬다.** 병합이 없으므로 서버본을 채택하면 `location.reload()`다. 한 사람이 두 기기를
        동시에 쓰는 일은 드물다고 본다.
    *   **인증이 없다.** `X-User-Id` 헤더 하나면 누구든 누구로도 들어간다 — 아이디 다섯을 아는 사람끼리 쓰는 서버라
        감수한다. 밖에 열 일이 생기면 그때 비밀번호나 계정 연결을 얹되 `userId`는 그대로 둔다.
    *   **NPC 마주침은 기기 간 결정성이 없다.** 시드에 `memory.name`이 들어가는 기존 규칙을 보존했다 — remote 상대만
        정렬된 id 쌍이다.

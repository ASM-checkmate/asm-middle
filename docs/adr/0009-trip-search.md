# ADR-0009: 여행지는 웹에서 찾아 오고, 일정은 여전히 규칙이 짠다

*   날짜: 2026-09-07
*   상태: 채택됨

## 배경

여행 일정은 전부 `frontend/src/sim/places.ts`에 박힌 13개 도시·150여 장소에서만 나왔다.
`travelOptions()`가 그 목록에서 목적지를 고르고, 도착 뒤의 하루도 `decide()`가 그 도시의 `PLACES`로
채우며, `journey.ts`는 `CITY_HUBS`로 공항·역 구간을 짠다. ADR-0006으로 로컬 모델 관문이 생겼지만
모델은 답장과 그림 읽기에만 쓰였고, **계획에는 들어오지 않았으며 외부 지식을 가져오는 길도 없었다.**
사용자가 "교토 가자"라고 하면 에이전트는 모른다고 할 수밖에 없었다.

한편 규칙 엔진은 이미 도시 키 기준으로 일반화돼 있다 — 제안·이동·시간대·호텔 어느 것도 도시 이름을
하드코딩하지 않는다. 부족한 것은 판단이 아니라 **데이터**다.

## 결정

**대화에서 가자고 한 도시를 백엔드가 웹에서 찾아 "도시 팩"으로 만들고, 프론트는 그것을 장소 표에
등록만 한다. 여행 카드·이동·도착지의 하루·호텔·귀환은 기존 규칙 엔진이 그대로 만든다.**

1.  **진입은 대화 실 하나다.** 답장 모델의 응답에 `trip`(도시 이름) 필드가 생긴다. 답장은 "오 좋다,
    찾아볼게"로 짧게 하고 모르는 장소·일정을 지어내지 않는다. 프론트는 아는 도시면 소원만 적고,
    모르는 도시면 `POST /api/trip/plan`을 부른다. tier가 off면 아무것도 안 한다 (그림 읽기와 같은 실패 경로).
2.  **백엔드는 고정 파이프라인이다.** Ollama Web Search 3회(한국어 둘·영어 하나, 병렬) → 로컬
    모델 1회(JSON 스키마로 장소 6~14개·호텔·허브·시간대 추출, 장소마다 근거 스니펫 번호) →
    Nominatim 지오코딩(순차, 초당 1회) → 조립·검증. 모델 주도 tool loop가 아니다.
3.  **지어낸 장소는 걸러진다.** 근거 번호가 범위 밖이면 버리고, 좌표는 도심 80km 안의 지오코딩 결과 >
    60km 안의 모델 근사값 > 버림. 지도(Nominatim)에 없는 이름은 대개 지어낸 이름이라 근사값만 있는
    장소는 셋까지만 받는다. 비허브 장소 6개 + 호텔 1개 + 허브(해외는 공항)가 없으면 팩이 아니다(422).
    하나쯤 섞여도 그것은 카드 한 장이고 `review` 문을 지난다.
4.  **팩은 브라우저에 남는다** (`theworld.places.v1`). `places.ts`가 모듈이 뜰 때 읽어 등록하므로
    스토어가 하이드레이트되기 전에 장소 id가 살아 있다. 백엔드도 `.cache/trip/`에 캐시해 같은
    도시를 두 번 검색하지 않는다.
5.  **소원은 카드의 순서만 바꾼다.** `memory.wish`가 7일 안이고 그 뒤 그 도시에 안 갔으면 다음 여행
    범주의 첫 카드가 그 도시다. 소원이 없으면 난수를 안 쓰므로 오늘의 하루는 그대로다.
6.  **끝나면 에이전트가 한 줄 덧붙인다.** "교토 찾아봤어. 기요미즈데라랑 니시키 시장 가고 싶다" /
    "찾아보려 했는데 잘 안 됐어". 시각은 답장 규칙과 같다 — 받을 수 있으면 금방, 아니면 막힌 게 끝난 뒤.

## 근거

*   **왜 규칙 엔진을 그대로 두는가.** "인식은 모델, 판단은 규칙"(ADR-0008). 모델은 장소를 찾아 올
    뿐이고, 언제 무엇을 하는가는 시드로 결정돼야 검사할 수 있고 새로고침해도 같은 하루다.
    규칙 엔진이 이미 도시 일반이라 데이터만 넣으면 여행 카드·비행·호텔·귀환이 전부 따라온다.
*   **왜 고정 파이프라인인가.** 단계마다 순수 함수라 기존 `buildPrompt`/`parse*` 검사 패턴으로
    Ollama 없이 시험할 수 있고, 비용(검색 3회·모델 1회·지오코딩 ≤16회)과 시간이 유계다. Ollama의
    `format`(스키마)과 `tools`는 한 호출에 잘 안 섞이고, 9B가 다단계 루프를 끌기엔 불안하다.
*   **왜 Ollama Web Search인가.** 이미 Ollama 위에 있고 키 하나로 되며 의존성 0 원칙(fetch만)에
    맞는다. 한도는 공개돼 있지 않아("개인용으로 넉넉한 무료 티어") 도시당 한 번만 부르도록 캐시한다.
    Tavily·Brave는 한도가 숫자로 명확하지만 키를 하나 더 관리해야 한다 — 한도 문제가 생기면 그때
    `search.ts` 하나만 바꾼다.
*   **왜 추출 모델도 tier를 따르는가.** 위키 본문을 검색 결과 삼아 교토를 돌려 본 결과(2026-09-07,
    M5 Pro 48GB): 9B는 추출 40초 + 실제 장소 10개에 "역 앞 카페" 같은 자리 채우기 셋(근사값 상한에 걸려
    셋만 남음), 한국어 표기가 자주 틀림(긴카쿠지 → 겐간지). 27B는 추출 53초 + 실제 장소 8개, 지오코딩
    실패 0, 표기가 정확. 지오코딩 실패가 시간을 먹어 전체 시간은 둘 다 1분 남짓으로 같다. 그래서 대화와
    같은 단계를 쓰고(`TRIP_MODEL`로 고정 가능), 이 비교도 이번 실험의 일부다.
*   **왜 브라우저에서 직접 지오코딩하지 않는가.** Nominatim은 식별 가능한 User-Agent와 초당 1회를
    요구하고 브라우저는 UA를 못 바꾼다. 검색 키도 서버에만 있어야 한다.
*   **왜 팩을 클라이언트에 두는가.** 장소 id가 사라지면 그 도시에서의 활동이 통째로 없어진다.
    "새로고침해도 같은 하루"는 장소 데이터가 하루보다 오래 살 때만 성립한다. 기기 간 결정성은
    보장하지 않는다 — 같은 도시라도 다른 백엔드는 다른 팩을 만들 수 있다.
*   **버린 선택지 — 모델이 tool loop로 검색·지오코딩을 스스로 부르기.** 몇 번 부를지, 언제 멈출지가
    모델에 달려 시간과 비용이 열린다. 검사도 어렵다.
*   **버린 선택지 — 여행 카드 아래 입력창.** 대화 실이 유일한 통로다(ADR-0002). 개발 패널에만
    입력을 둔다.

## 영향

*   `docs/CONTRACT.md`에 `trip` 필드와 `POST /api/trip/plan`. `backend/src/{search,geocode,trip}.ts`,
    `.env`에 `OLLAMA_API_KEY`·`NOMINATIM_CONTACT`·`TRIP_MODEL`·`CORS_ORIGIN`. `backend/.cache/`는 gitignore.
*   `places.ts`의 `CITY_HUBS`·`CITY_NAME_KO`·`CITY_TZ`가 가변 레지스트리가 된다 (이름은 그대로).
    `STAY_NIGHTS`는 `CITY_STAY`로 옮겨 같이 적힌다. 새 localStorage 키 `theworld.places.v1`,
    `Memory.wish`.
*   개발 패널에 `trip` 줄 — 도시 입력·등록된 도시·잊기. 잊기는 `resetDay`와 함께 간다(팩만 지우면
    그 도시의 활동이 조용히 사라진다).
*   감수하는 트레이드오프
    *   **1~2분 걸린다.** 검색 3초 + 추출 40~60초 + 지오코딩 ≤25초(순차 1.1초 간격). 대화는 멈추지 않고,
        끝나면 한 줄이 온다. 캐시되면 즉시다.
    *   **틀린 장소가 섞일 수 있다.** 근거 번호·반경·검증으로 거르지만 완벽하지 않다. 카드 한 장이다.
    *   **`comic.ts`의 도시별 문장(`CITY_FLAVOR`)이 없다.** 찾아 온 도시는 일반 해외 문장으로 나온다.
    *   **`CORS_ORIGIN` 기본이 `*`다.** 키는 서버에만 있지만 아무 탭이나 검색 한도를 쓸 수 있다.
        README가 개발 서버 주소로 좁히기를 권한다.
